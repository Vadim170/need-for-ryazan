# Формат мира (контракт пайплайн → игра), v1

Пайплайн пишет в `game/public/world/`. Vite отдаёт это как `/world/...`. Каталог генерируемый: в git не кладём, пересобирается командой `pipeline/build_world.py`.

## Системы координат
- Пайплайн: `pipeline/config.py` (`WORLD_CRS`), x — восток, y — север, метры, начало в Кремле (54.6363, 39.7496).
- Игра: `three.x = x`, `three.y = высота (м над уровнем моря минус BASE_HEIGHT)`, `three.z = -y`.
- `BASE_HEIGHT` указан в manifest; на него сдвигаем все высоты, чтобы числа были около нуля.
- **Все glTF уже в координатах игры** (Y-up, метры, позиция тайла запечена в вершины). Игра не делает никаких преобразований.

## Файлы

```
world/
  manifest.json
  terrain/heightmap.f32      // Float32 little-endian, row-major, строка 0 = север (min three.z)
  tiles/{ix}_{iz}.glb         // меши тайла: roads, buildings, … (отдельные именованные ноды); рельефа в тайлах нет (v1.1)
  roads/graph.json            // дорожный граф для спавна (и, позже, трафика)
```

### manifest.json
```jsonc
{
  "version": 1,
  "baseHeight": 90.0,                 // м, вычтено из всех высот
  "origin": { "lat": 54.6363, "lon": 39.7496 },
  "bounds": { "minX": -3250, "maxX": 4000, "minZ": -3250, "maxZ": 4250 },   // в координатах игры (фактические значения v1)
  "terrain": {
    "file": "terrain/heightmap.f32",
    "cols": 1451, "rows": 1501,       // фактические значения v1
    "cellSize": 5.0,                  // м
    "minX": -3250, "minZ": -3250      // three.x / three.z узла [row 0, col 0]
  },
  "tileSize": 250,
  "tiles": [ { "ix": 0, "iz": 0, "file": "tiles/0_0.glb", "minX": .., "minZ": .., "maxX": .., "maxZ": .. } ],
  "roads": { "file": "roads/graph.json" },
  "spawnPoints": [ { "x": .., "y": .., "z": .., "heading": .., "name": "площадь Победы" } ]   // heading: рад, 0 = смотрит на -Z (север), по часовой
}
```

Уточнения (v1, обратно совместимы):
- Индексы тайлов абсолютные: `ix = floor(x / tileSize)`, `iz = floor(z / tileSize)` (могут быть отрицательными, файл `tiles/-7_3.glb`). Тайл покрывает `[ix*250, (ix+1)*250] × [iz*250, (iz+1)*250]`. Границы мира кратны 250, тайлы покрывают их без пропусков.
- Узлы heightmap: `x = minX + col*cellSize`, `z = minZ + row*cellSize`; границы тайлов совпадают с узлами (51×51 узлов на тайл, соседние тайлы делят крайний ряд).
- Триангуляция ячейки рельефа (при построении меша и коллайдера в игре и при выборке высоты в пайплайне): диагональ от узла `(row, col)` к `(row+1, col+1)`, то есть треугольники `(r,c)-(r+1,c)-(r+1,c+1)` и `(r,c)-(r+1,c+1)-(r,c+1)`. Так же режет ячейки `HeightField` в Rapier, поэтому дороги лежат ровно на +0.05 м над коллайдером.
- `spawnPoints[].y` — высота поверхности дороги (рельеф +0.05 м); подъём машины на подвеску добавляет игра. Точка стоит в правой полосе, `heading` — вдоль полосы. Поле `name` есть только у именованных точек.
- Пустые ноды в тайле не пишутся (например, в поле нет `buildings`). Игра должна проверять наличие ноды.

### Ноды внутри tile .glb
- ~~`terrain`~~: **с v1.1 не пишется.** Игра строит и меш, и коллайдер рельефа из `heightmap.f32` (минус ~80 МБ). Включить обратно можно флагом `TERRAIN_MESH` в `build_world.py`. Тайл, где нечего писать, — валидный glb без нод и буферов.
- `roads`: проезжая часть, уложенная на рельеф (+0.05 м), на мостах — на настил. Два материала (два примитива одного меша; GLTFLoader даёт Group с двумя Mesh):
  - `road_asphalt`: ленты направленных рёбер. UV: u поперёк 0..1, v вдоль в метрах. **Двусторонняя дорога — это две ленты (по одной на направление)**: u = 0 у правой кромки (по ходу движения), u = 1 у оси дороги (для односторонней — у левой кромки). Число полос ленты — в graph.json (`lanesForward`/`lanesBackward`).
  - `road_junction`: площадки перекрёстков (формы SUMO), чуть выше лент (+0.01 м). UV = мировые (x, z) в метрах.
- `sidewalks`: тротуары (бордюр +0.15 м), материал `sidewalk`. В v1 не генерируются.
- `buildings`: экструзия футпринтов, материал `building_<type>` (apartments, house, commercial, garage, other). UV стен: u — метры по периметру, v — метры от низа стены; крыш — мировые (x, z). Отдельная нода `building_colliders`: упрощённые призмы (футпринт, упрощённый до 1 м: стены + крыша, **не обязательно выпуклые**) с `extras.collider = true`, без материала и нормалей. Игра делает из неё trimesh-коллайдеры и не рендерит.
- `bridges` (новое): визуальная плита мостов (низ и боковины), материал `bridge_concrete`. Верх настила лежит в `roads`.
- `bridge_colliders` (новое): замкнутые плиты настила мостов (верх = поверхность дороги на мосту, толщина 0.8 м, у наземных опор плавно сходит до 0.05 м на последних ≤12 м) с `extras.collider = true`. У наземной опоры поверхность моста совпадает с рельефом +0.05 м (ступенька ≤ 1 см), насыпь въезда вжата в heightmap. **Нужен обязательно**: под мостом heightmap остаётся рельефом долины, без этой ноды машина провалится. Правило для игры: любая нода с `extras.collider = true` — trimesh-коллайдер, не рендерится.
- `water`: поверхность рек и водоёмов (плоские полигоны на уровне воды), материал `water`, UV = мировые (x, z).
- Материалы: простые PBR-цвета. Текстуры подставит игра по имени материала.

### roads/graph.json
```jsonc
{
  "nodes": [ { "id": 0, "x": .., "y": .., "z": .. } ],          // координаты игры
  "edges": [ {
    "id": 0, "from": 0, "to": 1,
    "osmId": 123, "name": "Первомайский проспект", "highway": "primary",
    "lanesForward": 2, "lanesBackward": 2, "oneway": false, "width": 14.0,
    "bridge": false,                                             // новое: участок — мост (y по настилу)
    "points": [[x,y,z], ...]                                     // ось, координаты игры
  } ]
}
```
- Узлы — перекрёстки SUMO (`x, z` — центр, `y` — поверхность дороги). Ребро неориентированное: `lanesForward` — полосы в направлении `from → to`, `lanesBackward` — обратно; `oneway = true` ⇔ `lanesBackward = 0`.
- `points` — ось дороги (для двусторонней — линия между направлениями) от границы площадки перекрёстка `from` до границы `to` (не от центров узлов), шаг ~10 м, `y` = поверхность дороги (+0.05 м). Полоса `k` (0 = правая) направления `from → to` лежит справа от оси на `(k + 0.5) * width_lane`, где `width_lane = width / (lanesForward + lanesBackward)` (приближённо: ширина полосы зависит от класса). У односторонней дороги ось — середина проезжей части.
- `width` — полная ширина проезжей части (обе стороны), м.

### Дополнение: разметка, тротуары и бордюры (`markings`, `sidewalks`)
Обратно совместимо; строится `pipeline/world/markings.py` и `pipeline/world/sidewalks.py`, подробности в [stage1/markings.md](stage1/markings.md). Заменяет строку про `sidewalks` выше («в v1 не генерируются»): теперь генерируются.
- `markings` (новое): дорожная разметка, тонкие декали **ровно +0.02 м над фактическим мешем `roads`** (лент или площадок, на мостах над настилом), материал `road_marking` (белый). Один примитив на тайл, всё слито. UV: **u поперёк линии/полосы 0..1, v вдоль в метрах** (для износа и штрихов текстурой). У стрелок 1.18 u — поперёк габарита стрелки, v — метры от основания. Нормали есть. Состав: 1.1, 1.3, 1.5 (3/9 м), 1.2, 1.12, 1.14.1, 1.18. Внутри площадок перекрёстков продольных линий нет. Рекомендация игре: `depthWrite` можно оставить, но включить `polygonOffset` (−1, −1) и не отбрасывать тени; коллайдера нет.
- `sidewalks`: два материала (два примитива):
  - `sidewalk`: верх тротуара, рельеф **+0.15 м** (у пешеходных переходов опущен до +0.07 м с пандусами 1.5 м; на мосту — настил +0.10 м). Меш нарезан по треугольникам ячеек heightmap (каждый треугольник лежит в одной грани рельефа); рядом с дорогой, отклоняющейся от рельефа, верх плавно подтягивается к её уровню. UV = мировые (x, z) в метрах.
  - `curb` (новое имя материала): вертикальные грани по всему контуру тротуара (от рельефа −0.03 м до верха): со стороны дороги — бордюр, с внешней стороны — кромка. UV: u — метры вдоль контура, v — метры от низа грани. Нормали горизонтальные наружу (сглажены в вершинах контура).
- Тротуары и бордюры **не коллайдеры** (v1, аркада): машина проезжает «сквозь» бордюр по рельефу. Отдельной ноды `sidewalk_colliders` нет.
- Геометрия, пересекающая границу тайла: разметка (включая полосы зебр) режется по тайлам по середине сегмента (вылет за границу ≤ 1 м), тротуары — точно по границе тайла (на линии разреза граней бордюра нет); стрелка 1.18 целиком в тайле своего основания.

### Дополнение: дворы, площадки и пропсы (`areas`, `props/`)
Обратно совместимо; строится `pipeline/world/yards.py` (площадки, маски) и `pipeline/world/props.py` (расстановка), подробности в [stage1/yards.md](stage1/yards.md).

**Нода `areas`** в tile .glb (если в тайле есть площадки): плоские покрытия, уложенные **ровно на рельеф +0.03 м**. Полигоны порезаны по треугольникам ячеек heightmap (та же диагональ, что у коллайдера), поэтому каждая площадка параллельна рельефу без «прострелов»; меш слит по тайлу, вершины сварены. Один примитив на материал; POSITION + NORMAL (нормали рельефа, как у heightmap) + TEXCOORD_0 = мировые (x, z) в метрах. Материалы:
- `area_parking` — асфальт парковок (amenity=parking, кроме подземных/многоэтажных);
- `area_paving` — плитка: пешеходные зоны и площади (highway=pedestrian, place=square, marketplace), асфальтовые спортплощадки;
- `area_path` — дорожки: footway/cycleway/steps и мощёные path/track, буфер по ширине (footway 2.5 м, path 1.5 м, track 3 м, тег `width` важнее); `footway=sidewalk/crossing` пропущены (это тротуары);
- `area_playground` — детские площадки (OSM + процедурные во дворах), резиновое покрытие спортплощадок;
- `area_grass` — газон: парки, сады, landuse=grass, травяные поля (под лесом не кладётся — там рельеф);
- `area_dirt` — грунт: грунтовые тропы и треки, грунтовые спортплощадки.

Площадки не перекрываются (приоритет: playground > parking > paving > path > dirt > grass) и вырезаны по проезжей части (+0.3 м), площадкам перекрёстков, **футпринтам тротуаров** (тротуар главнее), зданиям и воде. Рекомендация игре: `polygonOffset` (−1, −1) от z-fighting с рельефом; коллайдера нет (машина едет по heightmap, разница 3 см).

**Пропсы** — инстансы, а не меши. Файл `props/{ix}_{iz}.json` на тайл (только если в тайле что-то есть); в manifest у тайла появляется поле `"props": "props/{ix}_{iz}.json"` (нет поля — нет пропсов).
```jsonc
{
  "version": 1, "ix": -8, "iz": 3,
  "instances": [ { "type": "tree_birch", "x": .., "y": .., "z": .., "rotY": 1.234, "scale": 1.07 },
                 { "type": "parked_car", ..., "seed": 40211 },          // доп. поля по типу — см. ниже
                 ... ],
  "segments":  [ { "type": "fence", "x1": .., "y1": .., "z1": .., "x2": .., "y2": .., "z2": .., "height": 1.8, "style": "metal" } ]
}
```
- `x, y, z` — координаты игры, точка основания модели. `y` = heightmap (+0.03, если точка на площадке `areas`); у фонарей на мостах — поверхность настила. Инстанс лежит в файле тайла, где стоит его точка.
- `rotY` — `object.rotation.y` (рад). Модель должна смотреть «вперёд» вдоль **локальной −Z**; при `rotY = 0` вперёд = север (−Z мира). Направление «вперёд» по типам — в таблице.
- `scale` — равномерный масштаб к номинальному размеру модели.
- Детерминированно: та же сборка даёт те же файлы (RNG с ключом по тайлу/объекту).

| type | Что | Номинал (scale = 1) | «Вперёд» (−Z модели) / доп. поля |
|---|---|---|---|
| `tree_birch` | берёза | высота ~15 м | случайный поворот |
| `tree_poplar` | тополь | ~20 м | случайный |
| `tree_maple` | клён | ~12 м | случайный |
| `tree_lime` | липа | ~15 м | случайный |
| `tree_pine` | сосна/ель (лес, хвойные из OSM) | ~18 м | случайный |
| `shrub` | куст (в т.ч. живая изгородь barrier=hedge, шаг 1.2 м) | ~1.5 м, Ø 2 м | случайный |
| `street_lamp` | уличный фонарь (процедурно, шаг 30–35 м; primary/secondary — с двух сторон, остальные — с одной) | опора ~9 м | консоль смотрит на дорогу |
| `traffic_light` | светофор на опоре, правая сторона каждого подхода у стоп-линии (перекрёстки SUMO `traffic_light`) | ~3.5 м | лицевая сторона к подъезжающим машинам; `lanes` — число полос подхода (≥3 — можно ставить консоль) |
| `bus_stop` | павильон остановки (OSM bus_stop/platform, сразу за тротуаром) | ~4×1.6×2.5 м | открытая сторона к дороге |
| `bench` | лавочка | 1.8 м | направление взгляда сидящего |
| `trash_bin` | урна | 0.4 м | — |
| `playground_set` | игровой комплекс (горка/качели) | габарит ~4×4 м | `variant` 0..7 — какую модель взять |
| `container_site` | контейнерная площадка (3–4 бака под навесом/оградой) | ~4×2 м | открытая сторона к проезду |
| `parked_car` | припаркованная машина (модель выбирает игра) | ~4.5×1.8 м | нос машины; `seed` 0..65535 — модель/цвет |

Сегменты: `fence` (barrier=fence, высота по умолчанию 1.8 м) и `wall` (wall 2.2, city_wall 3.5, retaining_wall 1.2 м; тег `height` важнее). Линии OSM порезаны на куски ≤ 4 м (чтобы следовать рельефу), концы на рельефе; там, где ограда пересекает проезжую часть (+0.8 м), она вырезана (ворота). `style` — необязательный (`fence_type`/`material` из OSM: `metal`, `chain_link`, `concrete`, `wood`…). Сегмент лежит в тайле своей середины. Коллайдеры для пропсов игра делает сама (по желанию: стволы, опоры, ограды).

Правило расстановки: внутри проезжей части и футпринта тротуаров пропсов нет; исключения — `street_lamp` и деревья вдоль магистралей стоят сразу за внешней кромкой тротуара, `traffic_light` — у бордюра на тротуаре (как в жизни).

**Проходы в оградах и калитки** (`pipeline/world/fence_gaps.py`, финальный проход после yards + streetlife, до записи props):
- Сегменты `fence`, `wall`, `lawn_fence`, `ped_fence`, `guardrail` разрезаны там, где их пересекает путь. В проходе сегментов нет: проход — это просто разрыв между соседними сегментами. Сегменты остаются в тех же props/*.json и в том же формате, только короче; кусков короче 0.25 м нет. `jersey_barrier` не режется.
- Ширина прохода поперёк пути: тропинки и дорожки 1.3–1.8 м, pedestrian 3 м, проезды/track: ширина проезжей части + 1 м (≥ 3.5 м), переходы 3 м, подъезды ≥ 1.6 м, остановки 4 м. Если путь пересекает ограду под углом θ, длина выреза вдоль ограды равна w / sin θ. `guardrail` режется только у переходов, проездов и остановок.
- **Пешеходный граф (`people/walk.json`) не пересекает оставшиеся ограды**: такие рёбра удалены (в `stats.edges_dropped_fence`).
- Новый тип инстанса **`fence_gate`** — открытая калитка/ворота в проходе: OSM `barrier=gate/swing_gate/wicket_gate/kissing_gate` на линии ограды, а также ворота на огороженных территориях (школы, сады, больницы, парки), где прохода не было.

  | Поле | Значение |
  |---|---|
  | `x, y, z` | **петля** (стойка) — у начала проёма, на рельефе |
  | `rotY` | направление закрытого створа вдоль ограды: локальная −Z модели смотрит от петли через проём |
  | `width` | ширина проёма, м (калитка 1.2–1.6, ворота 3–3.5) |
  | `height` | высота, м (по ограде, 1.0–2.5) |
  | `style` | `welded` (по умолчанию) \| `wood` \| `chain_link` |
  | `scale` | 1 |

  У `barrier=lift_gate` проход режется, но калитка не ставится: шлагбаум ставит streetlife (`barrier_gate`).

### Дополнение: улица — витрины, подъезды, клумбы, ограждения, фонари (`props/`)

Дверь ниже ряда окон 1-го этажа не пересекается с ними, потому что со зданиями v2 двери стоят на простенках между колонками окон (ширина двери ≤ шаг − ширина окна − 0.2 м), подъезды — по числу секций здания v2 (`entrances` реестра ЖКХ или длина / длина секции архетипа). ### Дополнение: пешеходная сеть (`people/walk.json`)
Обратно совместимо; строится `pipeline/world/walk_export.py` (вызов в `build_world.py` после пропсов), подробности в [stage2/people.md](stage2/people.md). Один файл на мир (~8 МБ JSON, ~157 тыс. узлов); manifest не меняется — игра просто пробует `people/walk.json` (нет файла — нет пешеходов).
```jsonc
{
  "version": 1,
  "kinds": ["sidewalk", "path", "crossing", "square", "yard", "link"],      // вид ребра = индекс
  "poiTypes": ["entrance", "shop", "bus_stop", "bench", "playground", "park"],
  "zones": { "center": 1, "commercial": 2, "residential": 4, "park": 8, "industrial": 16, "yard": 32 },
  "nodes": [x, y, z, x, y, z, ...],     // координаты игры; y — поверхность, по которой идут ноги
  "zone":  [bits, ...],                  // на узел: битовая маска зон (плотность пешеходов)
  "edges": [a, b, kind, crossing, ...],  // по 4 числа: узлы, вид, id перехода (−1 — не переход); граф неориентированный
  "crossings": [ { "id": 0, "a": 123, "b": 456,          // узлы графа у бордюров
                   "x": .., "y": .., "z": ..,            // центр (на проезжей части)
                   "width": 7.0,                          // ширина проезжей части, м
                   "road": 812,                           // id ребра roads/graph.json, которое пересекают
                   "junction": 345,                       // id узла roads/graph.json со светофором, −1 — нерегулируемый
                   "signal": true,                        // регулируемый (светофор SUMO рядом или тег OSM crossing=traffic_signals)
                   "marked": true,                        // зебра 1.14.1 (из разметки); false — переход «по линии тротуаров» на перекрёстке
                   "sumoJunction": "cluster_…", "sumoEdge": "-1234#2" } ],   // id SUMO для traffic/signals.ts pedestrianWalk
  "pois": [ { "t": "bench", "x": .., "y": .., "z": .., "n": 789, "r": 1.57 } ],   // n — узел графа, к которому POI привязан
  "stats": { ... }                       // сводка сборки (длины по видам, число компонент и т.п.)
}
```
- `y` узла: рельеф (heightmap, та же триангуляция) + подъём поверхности: тротуар **+0.15** (в зоне перехода опущенный бордюр +0.07…+0.15), проезжая часть (переходы, дворовые проезды) +0.06, всё остальное (дорожки, площади, газон) +0.03. Рёбра не длиннее 8 м — между узлами высоту можно интерполировать линейно.
- Виды рёбер: `sidewalk` — оси тротуаров (кромка проезжей части + половина ширины тротуара, только там, где лежит футпринт тротуара) и дуги вокруг площадок перекрёстков, а также пути OSM `footway=sidewalk`; `path` — пешеходные пути OSM (footway/path/steps/cycleway); `crossing` — переход от бордюра до бордюра; `square` — решётка 8 м на пешеходных площадях; `yard` — вдоль края дворовых проездов (service, living_street); `link` — короткие связки (≤ 8 м, ≤ 12 м от концов дворовых проездов), не пересекающие проезжую часть автодорог, здания и воду.
- Переходы: все зебры из разметки (узлы OSM highway=crossing) + на каждом «рукаве» регулируемого перекрёстка без зебры в OSM (`marked=false`, `signal=true`) + на нерегулируемых перекрёстках ≥ 3 рукавов на дорогах ≤ 11 м (`marked=false`, `signal=false`). Регулируемость зебры: ближайший конец её дороги — узел SUMO `traffic_light` не дальше 45 м по оси. Фаза пешехода: `traffic/signals.ts → pedestrianWalk(sumoJunction, sumoEdge)`.
- `pois[].r` — `rotation.y`, куда смотрит человек на месте: у лавки — взгляд сидящего (как у пропса), у остановки — к дороге, у входа — наружу от фасада. Входы: OSM `entrance=*` (кроме emergency/service/garage), иначе процедурно 1–4 точки на фасадах жилых/коммерческих домов (≥ 150 м²), обращённых к сети; у коммерческих тип `shop`. Магазины — узлы OSM shop/office/amenity (кафе, аптеки, банки…), точка на фасаде их дома.
- Граф не обязательно связный (река, железная дорога, магистраль без переходов); компоненты короче 150 м выброшены. Цели игра выбирает внутри своей компоненты.

### Дополнение: трафик (`traffic/net.json`, `traffic/geom.bin`)
Обратно совместимо; строится `pipeline/world/lanes_export.py` (вызов в `build_world.py` после пешеходов) из `net.xml` SUMO и отношений OSM `route=*`. Подробности и поведение игры — [stage2/traffic.md](stage2/traffic.md). Два файла на мир (~5.4 МБ JSON + ~2.5 МБ бинарных точек).

`geom.bin` — Float32 little-endian, тройки `x, y, z` в координатах игры: ломаные всех полос и соединений подряд. `y` — **поверхность фактического меша `roads`** (лента/площадка перекрёстка, на мостах — настил; та же выборка, что у разметки, без подъёма декали), точки через ≤ 4 м, упрощены Дугласом–Пекером в 3D с допуском 4 см.

               "from": 12, "to": 13,        // индексы junctions
               "hw": "primary", "prio": 10, "name": "Первомайский проспект",
               "lanes": [100, 101],         // индексы lanes, 0 = правая полоса
               "osmId": 380039823, "bridge": false,
               "main": 1 } ],               // 1 — ребро в главной сильно связной компоненте (по полосам для легковых): туда ездит случайный трафик
  "lanes": { "edge": [..], "index": [..],   // ребро и номер полосы (0 — правая)
             "speed": [..],                 // м/с, ограничение SUMO (по типу дороги / maxspeed)
             "length": [..],                // м (2D)
             "width": [..],
             "cls": [..],                   // биты: 1 — легковые, 2 — автобус/троллейбус, 4 — только служебный (delivery: service-дороги)
             "p0": [..], "pn": [..] },      // первая точка в geom.bin и число точек
  "conns": { "from": [lane..], "to": [lane..],   // соединение полоса → полоса через перекрёсток
             "junction": [..],               // индекс узла
             "length": [..], "speed": [..],  // по внутренней полосе SUMO (скорость поворота)
             "p0": [..], "pn": [..],         // ломаная внутренней полосы (цепочка internal-полос SUMO склеена)
             "tl": [..], "link": [..],       // индекс в tls и linkIndex (−1 — нерегулируемое)
             "dir": "srl…",                  // по символу на соединение: s прямо, r/l направо/налево, R/L плавно, t разворот
             "state": "MmM…",                // приоритет SUMO: M главная, m второстепенная, = равнозначная, o/O светофор выключен
             "resp": [[conn..]],             // кому уступает (SUMO request.response), индексы conns того же узла

                "ref": "1", "name": "Троллейбус №1: …",

Кольцевые пути (замкнутые) не якоря — через них проходит кратчайший путь. Остановки — узлы `stop*` (иначе платформы), проецируются на правую полосу рёбер куска монотонно, ≤ 25 м.

### Дополнение: здания v2 — архетипы, крыши, балконы (`buildings`, `balconies`)
Строится `pipeline/world/city_buildings.py` (+ `archetypes.py`, `building_geom.py`; флаг `BUILDINGS_V2` в `build_world.py`), подробности — [stage2/buildings.md](stage2/buildings.md). Заменяет описание `buildings` выше; `building_colliders` — как раньше (призмы до верха стен, без крыш). Игра: `game/src/world/building-material.ts` (материал + подготовка геометрии), `balconies.ts`.

**Нода `buildings`**: один примитив на тайл, материал `building` (старые `building_<type>` больше не пишутся; игра их по-прежнему понимает). Вершины не сварены (плоские нормали граней). Атрибуты:

| атрибут glTF | тип | смысл |
|---|---|---|
| `POSITION`, `NORMAL` | float3 | как везде (координаты игры) |
| `TEXCOORD_0` | float2 | стены: **u — м от начала этой стены** (каждое ребро футпринта — своя стена), **v — м от пола 1-го этажа** (в цоколе v < 0). Скаты: u — м вдоль карниза, v — м вверх по скату. Плоские крыши — мировые (x, y) пайплайна = (x, −z) игры. Купола: u = угол·R, v = м по высоте |
| `TEXCOORD_1` | float2 | стены: (длина стены, м; высота этажа, м). Остальное — (0, 0) или (длина, 3) |
| `COLOR_0` | ubyte4 normalized, **linear** | цвет фасада у стен/карнизов, цвет кровли у крыш/куполов |
| `_ARCH` | ubyte4 | (архетип, seed 0..255, часть, этажность). GLTFLoader кладёт как `_arch` |

Архетипы: 0 other, 1 panel5 (1-464), 2 brick5 (1-447), 3 panel9 (II-49/121), 4 tower (П-44Т, точечные), 5 stalinka, 6 merchant (дореволюционные), 7 house (частный), 8 modern, 9 commercial, 10 garage (ряды ГСК), 11 industrial, 12 church, 13 school, 14 public, 15 shed.
Части: 0 стена, 1 участок стены с витринами 1-го этажа (ровно там, где у слоя улицы есть запись `storefronts`; стена режется на участки, u сквозное), 2 глухая стена (брандмауэр: вплотную к соседнему зданию — без окон), 3 плоская крыша, 4 скат, 5 карниз/парапет/подшивка, 6 короб на крыше (машинное отделение лифта, выход, вентшахта), 7 фронтон, 8 купол/крест, 9 барабан/колокольня.
Сетка окон, которую рисует шейдер и под которую ставятся балконы: шаг `S` по архетипу (`STYLE` в `archetypes.py`), колонок `n = floor((L − 1.2)/S)`, первая колонка с `start = (L − n·S)/2` от начала стены; этаж `k` — `v ∈ [k·fh, (k+1)·fh)`, этажей — `_ARCH.w`.

**Нода `balconies`** (если в тайле есть): примитив **POINTS** (mode 0), одна точка — вертикальная стопка балконов:
- `POSITION` — середина низа плиты нижнего балкона в плоскости фасада;
- `_BAL` float4: (тип 0 открытый / 1 застеклённый / 2 лоджия, `rotY` — наружу от фасада по правилу пропсов (локальная −Z), число этажей в стопке, высота этажа м);
- `_BAL2` float4: (ширина м, вынос м, доля застеклённых жильцами 0..1 — для типа 0, seed 0..1).
Балкон этажа `i` стоит на `y + i·fh`. Стопка лежит в тайле своей точки. Игра разворачивает стопки в инстансы (один InstancedMesh на тайл, виден до ~420 м). Козырьки подъездов здесь не генерируются (см. `entrances` выше).

### Дополнение: высотная структура дорог и сооружения (`roads/structures.json`, нода `bridges`)
Обратно совместимо; строится `pipeline/world/structures.py`, подробности в [stage2/terrain-v2.md](stage2/terrain-v2.md).

**Нода `bridges`** теперь содержит все инженерные сооружения дорожной сети (не только плиту настила). Материалы (примитивы одного меша):
- `bridge_concrete` — плита настила (как раньше), консоли тротуаров на мостах, опоры (восьмигранные колонны Ø 1.2 м через ≤ 6 м поперёк + ригель 1.0 м под плитой, шаг пролётов ~28 м), устои на границе пролёт/насыпь;
- `bridge_railing` (новое) — ограждение/парапет по внешним кромкам мостов и дамб: вертикальная стенка 0.15 × 1.1 м (верх, обе стороны, торцы). UV: u — метры вдоль, v — абсолютная высота в метрах (для текстуры балюстрады с альфа-тестом удобнее `v − min`). Рекомендация игре: металлический/бетонный парапет, `side: DoubleSide` не нужен (стенка замкнута);
- `retaining_wall` (новое) — подпорные стены: вдоль выемок дорог (рельеф в 8 м за кромкой выше дороги на ≥ 2.2 м на ≥ 16 м) и боковые стенки дамб из `data/overrides/elevation.json` (ул. Ленина над Лыбедским бульваром). Толщина 0.5–0.6 м, низ на 0.3–0.5 м ниже рельефа. UV как у ограждения: u — метры вдоль, v — абсолютная высота, м.

Пока у игры нет этих материалов, нода склеивается с материалом `bridges` (бетон) — это нормально. Ж/д мосты строит `world/railways.py` (свой раздел контракта).

**Коллайдеры:** ограждения, колонны опор и устои добавлены в `bridge_colliders` (`extras.collider`), так что с моста нельзя съехать сквозь парапет, а в опору под путепроводом можно врезаться. Опоры не ставятся в коридоры наземных дорог (ось ± полуширина + 1.5 м) и путей ж/д (± 3 м).

### Дополнение: железная дорога (`railway`, `railway_colliders`, `rail/net.json`)
Обратно совместимо; строится `pipeline/world/railways.py` (два вызова в `build_world.py`: `prepare()` — после вжатия дорог, `build()` — после сооружений), подробности — [stage2/rail.md](stage2/rail.md). Игра: `game/src/rail/`. Нет файла `rail/net.json` — поездов нет.

**Рельеф.** Коридоры путей вжаты в heightmap: под осью и в полосе ±3 м рельеф = **основная площадка = головка рельса − 0.65 м**, дальше насыпь/выемка с откосом ~1:1.5 (до 32 м). Ячейки проезжей части (вес вжатия дорог ≥ 0.5) не меняются, кроме полосы ±3.5 м под пролётами путепроводов (там дорога — настил, рельеф опускается до площадки). Пролёты ж/д мостов не вжимаются.

**Нода `railway`** (материалы — отдельные примитивы; координаты игры, нормали есть, кроме `rail_steel`):
| материал | что | UV |
|---|---|---|
| `rail_ballast` | балластная призма: верх ±1.75 м на головка − 0.21, откосы до рельефа (на мосту — до плиты); на проезжей части переезда нет | u — м поперёк от оси (−2.41…2.41), v — м вдоль |

Обратно совместимо; строится `pipeline/build_landcover.py` (классификатор, `pipeline/landcover/`) и хуком `pipeline/world/landcover_veg.py` в `world/props.py` (деревья и заросли), подробности — [stage3/landcover.md](stage3/landcover.md). **Карта покрова** (вне `world/`, как `veg.png`): `game/public/world-veg/landcover.png` + `landcover.json` (`cell` = 2 м, `cols`, `rows`, `minX`, `minZ` — координаты игры угла ячейки [0, 0], `classes` — имена по кодам). PNG 8 бит серый, значение = код класса, строка 0 = север (min three.z), столбец 0 = min x. Коды: 0 нет данных, 1 `canopy` (кроны лиственных), 2 `conifer` (хвойных), 3 `thicket` (заросли), 4 `meadow` (высокая трава/луг/поле), 5 `lawn` (кошеный газон), 6 `garden` (огород/грядки), 7 `bare` (голый/вытоптанный грунт), 8 `sand`, 9 `gravel` (щебень, промплощадка, балласт), 10 `water`, 11 `paved`, 12 `building`. Внутри зданий/проезжей части/воды OSM код — их класс. Игра красит по карте голый рельеф (`terrain`) и выбирает траву (`grass.ts`); нет файла — всё как раньше.

**Новые инстансы** (`props/{ix}_{iz}.json → instances`):

| type | Что | Номинал (scale = 1) | Доп. поля |
|---|---|---|---|
| `tree_negundo` | клён ясенелистный (Acer negundo): 3–5 кривых наклонных стволиков от земли, повислые ветви, светлая перистая листва; осенью жёлтый, зимой голые спутанные серо-зелёные прутья | ~7 м, крона Ø ~5 м | случайный поворот; коллайдер — цилиндр r ≈ 0.45·scale (пучок стволиков) |
| `thicket` | клумпа зарослей (клён ясенелистный, ивняк, молодняк): ~11 стволиков и сплошная листва | `radius` — радиус клумпы, м (1.9–2.9; номинал 2.2), `height` — высота, м (3.2–8; номинал 5), `seed` 0..65535 | масштаб модели по XZ = radius/2.2, по Y = height/5; `scale` всегда 1. Клумпы стоят через ~4 м и перекрываются — массив сплошной. Коллайдер — цилиндр r = 0.78·radius, высота 2.6 м: пешком (игрок, пешеходы) не пройти; машина продавливает тонкие клумпы (порог 4 км/ч, −9 км/ч на клумпу, клумпа пригибается), густые (`radius ≥ 2.5` и `height ≥ 5.2`) — только с разгона ≥ 55 км/ч и −45 км/ч |

Процедурные деревья (`tree_*` из таблиц `SCATTER` и вдоль магистралей) теперь ставятся, только если на спутнике в радиусе 2 м (у улиц 3 м) есть кроны/заросли или класс неизвестен; в вершинах крон, где деревьев нет, добавляются деревья по кронам (порода: хвойные → `tree_pine`, светлая мелкая крона → `tree_birch`, высокая тень → `tree_poplar`, иначе клён/липа/берёза; `scale` — по радиусу кроны).
