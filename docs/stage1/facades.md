# Цвет фасадов по панорамам Яндекса (stage 1)

Цель: для каждого здания OSM получить реальный цвет фасада (и грубый класс материала), чтобы генератор мира красил стены не только по типу здания. Источник: уличные панорамы Яндекса, **только для личного использования**.

Результат: `data/processed/building_facades.json`. Здания без наблюдений в файл не попадают, для них генератор берёт цвет по умолчанию для типа.

## Формат

```json
{
  "meta": {"source": "...", "method": "docs/stage1/facades.md", "stats": {...}},
  "buildings": {
    "w103761249": {"color": "#cea948", "confidence": 0.71, "samples": 2, "material": "plaster_yellow",
                   "levels_est": null, "lab": [70.1, 2.3, 45.0], "spread": 4.1, "lit_samples": 1}
  }
}
```

- Ключ: `w<id>` для пути OSM, `r<id>` для мультиполигона-отношения (`osm.buildings()` в `world/osm.py` отдаёт голый id; при интеграции нужно добавлять префикс по типу).
- `color`: sRGB, взвешенная медиана наблюдений в Lab. Это **цвет пикселей панорамы**, а не альбедо: значения обычно темнее, чем «на глаз» (медиана L≈45–55). Если в игре стены выглядят тёмными, при интеграции можно поднять яркость (×1.2–1.4 по L), не меняя оттенок.
- `confidence` (0..1): растёт с суммарным весом наблюдений (дальность, угол, число пикселей, доля «стенных» пикселей) и падает при разбросе между наблюдениями. Одиночное наблюдение даёт ×0.75, только теневые наблюдения дают ×0.8. **Рекомендуемый порог для использования: ≥ 0.5.** Ниже 0.3 это часто деревья, заборы или соседний дом.
- `samples`: число наблюдений (пара «панорама × освещённость фасада»), прошедших отсев выбросов.
- `material`: эвристика **только по цвету** (фактуру кирпича на этом разрешении не видно): `brick_red`, `white_silicate_or_plaster`, `panel_grey`, `dark_grey`, `plaster_beige`, `plaster_yellow`, `plaster_pink`, `plaster_colored`. Белый силикатный кирпич, белая штукатурка и светлая панель цветом не различаются.
- `levels_est`: всегда `null`. Этажность по рядам окон не оценивалась: качаем только полосу панорамы от −12° до +37°, верхние этажи в неё не попадают.
- `lab`, `spread`, `lit_samples`: служебные поля для отладки.

## Метод

### 1. Панорамы (`facades/yandex.py`)
Свой минимальный клиент по мотивам `sk-zk/streetlevel` (MIT). Сам `streetlevel` не импортируется: на Mac его модуль `exif` требует `pyexiv2` с отсутствующей dylib.
- Поиск: `https://api-maps.yandex.ru/services/panoramas/1.x/?l=stv&lang=en_US&ll={lon},{lat}&origin=userAction&provider=streetview`. Ответ содержит `Data.panoramaId`, `Point.coordinates`, `EquirectangularProjection.Origin`, `Images.{imageId,Zooms,Tiles}`. Если панорамы рядом нет, приходит `404`.
- Тайлы: `https://pano.maps.yandex.net/{imageId}/{zoom}.{x}.{y}`, размер 256×256. Берём зум с шириной ≈1792 px: у автомобильных камер это z3 (1792×619), у сферических z2 (1792×896). Качаем **только ряд тайлов 1**, это углы места от +38.6° до −12.9° (7 тайлов на панораму). Максимальный зум не трогаем.
- Точки опроса: оси автодорог OSM (primary…residential, living_street, pedestrian; без service) через каждые 50 м, с дедупом. Панорамы дедупятся по id, затем прореживаются до расстояния ≥ 15 м (оставляем самую свежую).
- Вежливость: свой User-Agent, ограничитель 4–5 запросов/с на процесс, 5 повторов с экспоненциальной паузой. Кэш `data/raw/panoramas/`: `lookup.json` (точка → id), `meta/<id>.json`, `img/<id>_z<z>_r<r0>-<r1>.jpg`. У старых панорам (2020 г.) тайлы стабильно отдают HTTP 500. Такие помечаются `img/<id>.bad` и больше не запрашиваются (50 шт.). Чтобы повторить, удалите `.bad`.

### 2. Конвенции проекции (проверено)
- Пиксель `x=0` смотрит на азимут `Origin[0]` (градусы по часовой от севера), азимут растёт вправо: `u = ((bearing − Origin[0]) mod 360) · W/360`.
- Верх изображения соответствует зениту, масштаб `W/360` px на градус по обеим осям: `v = (90 − elev) · W/360`. У автомобильных панорам низ обрезан (H≈0.346·W), у сферических H=W/2. `Origin[1]` в проекции не участвует.
- Как проверяли: (а) у двух панорам положение солнечного диска совпало с расчётным азимутом и высотой Солнца на момент съёмки с точностью ≈1–3°. Время съёмки — unix-время из суффикса `panoramaId`; `Data.timestamp` это округлённая дата, по нему считать нельзя. (б) Проекции футпринтов OSM (основание и верх) совпадают с углами домов на ~30 просмотренных контрольных кропах. Остаточная ошибка 1–2°, у пешеходных панорам больше.
- Высота камеры: 2.6 м у автомобильных панорам, 2.0 м у полносферных (пешеходные/сторонние). Рельеф берётся из `fabdem_grid10m.tif`.

### 3. Видимость и выборка пикселей (`facades/analyze.py`)
Для каждой панорамы:
1. Берутся все футпринты в радиусе 65 м. Из камеры пускаются 1440 лучей (шаг 0.25°) против всех рёбер футпринтов, и на каждый луч находится ближайшее попадание. Учитываются дальность 4–60 м и угол к нормали фасада не больше 72°. Крайние бины каждого фасада отбрасываются (углы зданий). Если камера стоит внутри футпринта, панорама пропускается.
2. Вертикальное окно на фасаде отсчитывается от основания, а основание — это рельеф в точке попадания луча:
   - высота из тегов: 3 м … min(высота − 1, 12) м;
   - высота неизвестна, жилое здание или футпринт > 400 м²: 3–8 м;
   - высота неизвестна, прочие здания: 2–4.5 м (одноэтажки часты, а завышенная высота даёт небо или дом за зданием).
   
   Кроме того, низ окна поднимается не ниже +1° над горизонтом камеры, чтобы срезать заборы, машины и кусты вдали.
3. Из пикселей убираются: небо (непрерывный сверху «небесный» прогон в столбце, плюс b* < −20), листва (оттенок 100–200° при C>7 или a* < −6), глубокие тени и стекло (L<22), пересвет (L>97).
4. Цвет наблюдения ищется k-means (k=4) в Lab. Выбирается кластер с наибольшей долей, умноженной на бонус за насыщенность, среди кластеров с долей ≥ 15% и L ≥ 33. Окна, рамы и белый декор нейтральны, а окрашенная стена хроматична. У серых и белых домов побеждает самый крупный кластер.
5. Освещённость: по времени съёмки считается положение Солнца (`facades/sun.py`, NOAA). Фасад «на солнце», если его внешняя нормаль смотрит на Солнце (cos > 0.12) и небо в полосе ясное (медиана b* неба < −12). Наблюдения раздельные: (здание, освещён/в тени).

### 4. Агрегация
- Поправка «тень → солнце» калибруется по зданиям, у которых есть и освещённые, и теневые наблюдения хорошего качества (1036 зданий): L×1.10, a*+0.5, b*+3.6. Теневая сторона в ясный день синеватая и темнее. Поправка применяется к теневым наблюдениям ясных панорам.
- Веса: cos угла × 1/(1+(d/25)²) × насыщение по числу пикселей × доля «стенных» пикселей × доля выбранного кластера. Освещённые ×1, теневые ×0.5, пасмурные ×0.6.
- Итог: взвешенная медиана L, a*, b*. Выбросы дальше 18 ΔE отбрасываются, медиана пересчитывается.

## Качество (ручная проверка контрольных кропов)
Просмотрено ~35 кропов `facades_check/*.png`. Сверху сырой кроп, снизу проекция футпринта (жёлтым — основание и верх по OSM, красным — окно выборки), внизу образцы цвета (итог и это наблюдение).
- **Хорошо (примерно половина, почти все с conf ≥ 0.5):** жёлтые и охристые штукатурные дома (Право-Лыбедская 26 → `#cea948`), серый силикатный кирпич (Попова 19/43 → `#898677`), белые дома и церкви, оранжевый кирпич (Пожалостина 46 → `brick_red`), бежевые сталинки.
- **Плохо:** здание закрыто деревьями или забором (цвет листвы или забора, conf обычно < 0.3); двухцветные дома (цоколь и верх разного цвета) — берётся пояс 3–8 м, и это может быть цоколь; тёмные витрины первого этажа уводят в `dark_grey`; гаражи (в кадре машины и асфальт); неверная или устаревшая геометрия OSM (на месте футпринта другой дом).
- Ориентация и привязка надёжны: систематического сдвига на кропах не видно.

## Известные проблемы
- Цвет = пиксели фото с автоэкспозицией камеры Яндекса, а не альбедо. Летние солнечные панорамы контрастнее, зимние и пасмурные серее. Пасмурные наблюдения весят меньше, но не корректируются.
- `dark_grey` (≈480) — в основном ошибки: тень, витрины, деревья. Лучше брать для них цвет по умолчанию, если confidence < 0.6.
- Неизвестная высота (79% зданий без `building:levels`) приводит к консервативному окну выборки; у многоэтажных домов с цокольным этажом другого цвета итог может уйти в цоколь.
- Из исторических панорам (`HistoricalPanoramas`) используется только самая свежая. Безлистные (зимние) панорамы могли бы снять проблему деревьев, но это не сделано.
- Оценка этажности не делалась (`levels_est = null`).
- 538 точек вдоль дорог без панорам, проезды `service` не опрашивались.

## Как доснять остальное
Дворовые проезды (`highway=service`): ещё ≈ 6.9k точек опроса, по грубой оценке ~1.5k новых панорам, ≈ 19k запросов (~1–1.5 ч). Чтобы включить, добавьте `"service"` в `SAMPLE_HW` (`facades/scene.py`). Яндекс-машины во дворы заезжают редко, прирост будет в основном по крупным проездам.

## Как перезапустить

```bash
cd pipeline
uv run python build_facades.py fetch --area core          # ядро (~35 мин с нуля)
uv run python build_facades.py fetch --area all --rate 5  # весь bbox (~1.5 ч с нуля; кэш переиспользуется)
uv run python build_facades.py analyze check              # анализ (~3–5 мин) + контрольные картинки и карта
```

- `fetch` дописывает список панорам в `data/processed/facades_panos.json`; `analyze` работает только по кэшу, в сеть не ходит.
- Выход: `data/processed/building_facades.json`, сырые наблюдения `data/processed/facades_obs.json`, контроль `data/processed/facades_check/*.png` (`--n-check N` случайных зданий), карта `data/processed/facades_map.png` (тёмно-серый = нет данных, голубые точки = панорамы).
- Параметры окна выборки и фильтров заданы константами в начале `facades/analyze.py` и в `facades/color.py`.
- Код: `pipeline/build_facades.py`, `pipeline/facades/` (`yandex.py` клиент и кэш, `scene.py` здания, рельеф и точки опроса, `proj.py` проекция, `sun.py` Солнце, `color.py` Lab, фильтры и материал, `analyze.py` видимость и агрегация, `viz.py` контроль). Используется только чтение `world/osm.py` (`OsmData`, `parse_numbers`).
