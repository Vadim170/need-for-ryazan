# Этап 1: правки дорог по аэрофотоснимку (overrides)

Слой ручных правок атрибутов дорог OSM, проверенных по ортофото Яндекса (`data/processed/ortho`, см. [satellite.md](satellite.md)). Он применяется в сборке мира до netconvert, поэтому все дальнейшие шаги видят правки так, будто теги стоят в самом OSM: полосы SUMO, разметка (в т.ч. стрелки по `turn:lanes`), тротуары, дворы, трафик. Формат внутренний для пайплайна, контракт мира (`world-format.md`) не меняется.

## Файлы

- `data/overrides/roads.json` — сами правки.
- `pipeline/world/overrides.py` — применение к `OsmData` (на месте).
- `pipeline/build_world.py` — точка подключения: две строки сразу после чтения OSM.
- `pipeline/verify_junctions.py` — кропы ортофото с осями OSM и полосами SUMO; режим `--checks` рисует «снимок / до / после» → `data/processed/junctions_check/*.png`.

Сопутствующие изменения:
- `world/sumo_net.py`: убран флаг `--ignore-widths` (теги `width` из OSM по-прежнему вырезаются при записи `roads.osm`, так что действуют только ширины из overrides; остальные ширины SUMO не изменились — проверено сравнением `net.xml`), добавлен `--osm.turn-lanes` (соединения полос строятся с учётом `turn:lanes`, включая уже имеющиеся в OSM; без этого стрелки разметки брали направления из угаданных соединений).
- `world/osm.py`: `write_filtered_osm` оставляет тег `width`, если путь помечен `nfr:width` (метку ставит `overrides.py`).

## Формат `roads.json`

```json
{
 "version": 1,
 "ways":  [{"id": 96060013, "set": {"lanes": 3}, "del": ["turn:lanes"], "conf": "high", "why": "..."}],
 "nodes": [{"id": 123, "move": [dx, dy]}, {"id": 456, "xy": [x, y]}],
 "add":   [{"id": "slip_x", "nodes": [111, [x, y], 222], "tags": {"highway": "primary_link", "oneway": "yes", "lanes": 1}}],
 "checks":[{"name": "pl_pobedy", "title": "пл. Победы", "at": [-2470, -790], "size": 220}]
}
```

- **ways** — по id пути OSM. `set` ставит/заменяет теги (`lanes`, `lanes:forward`/`backward`, `turn:lanes`, `turn:lanes:forward`/`backward`, `oneway`, `width`, `highway`, …; числа можно писать числами), `del` удаляет теги.
  - `width` — полная ширина проезжей части пути в метрах; netconvert делит её поровну между всеми полосами пути (у двусторонней — между обоими направлениями). Удобно для улиц, где асфальт шире, чем `полосы × ширина класса`, но полос больше не становится (парковка у кромки).
  - `split: [node, …]` + `parts: [{set, del}, …]` — разрезать путь в узлах и дать кускам свои теги (например, карман поворота только на последних 60 м). Первый кусок сохраняет id, остальные получают синтетические id ≥ 9·10¹¹ с тегом `nfr:parent`; в `graph.json` `osmId` у них синтетический.
- **nodes** — сдвиг узла OSM в мировых метрах (`move`) или абсолютная позиция (`xy`). Узел общий для всех путей, которые через него проходят.
- **add** — новый путь (пропущенный съезд и т.п.); `[x, y]` в списке узлов создаёт новый узел.
- **checks** — список видов для `verify_junctions.py --checks`.
- `name`, `why`, `conf` (high / medium) — комментарии, код их не читает.

Пропавшие id (OSM обновили) не роняют сборку: в логе печатается `НЕ НАЙДЕНО: …`.

Правки на уровне перекрёстков (радиус, свои соединения SUMO) в формат не вошли: проверка показала, что формы площадок netconvert на проверенных узлах совпадают с асфальтом с точностью ~2 м, а соединения теперь задаются через `turn:lanes`. Если понадобятся, их проще добавить вторым проходом netconvert с plain-xml патчем (`--sumo-net-file net.xml --node-files … --connection-files …`).

## Как делались правки

1. Кропы 160–260 м вокруг ~33 узлов и магистралей (`verify_junctions.py --at X,Y --size S [--nodes]`): слева снимок (z19, 0.25 м/px в ядре, иначе 0.5), справа — оси OSM с id и числом полос и полосы SUMO. Плюс «выпрямленные» полосы снимка вдоль каждого пути с засечками границ полос SUMO (0.12 м/px) и поперечный профиль яркости (пики — линии разметки).
2. Полосы считались по линиям разметки и ширине проезжей части; для разделённых дорог — от осевой/разделителя до кромки.
3. Пробовался полуавтоматический замер ширины асфальта (поперечные сечения каждые 3 м, «асфальт» = серый пиксель, близкий к медианному цвету на оси, медиана по сечениям) для residential/tertiary/unclassified без `lanes` в ядре. Результат шумный: припаркованные машины, тротуары того же цвета и тени деревьев дают разброс IQR 3–8 м. Принят только один путь, подтверждённый глазами (Маяковского 81239854); остальные — нет. Для этого класса дорог надёжнее ручной просмотр.
4. Стрелки на асфальте при 0.17–0.25 м/px не читаются уверенно (машины, износ), поэтому `turn:lanes` не добавлялись.

## Что осталось

- `turn:lanes` по снимку не добавлены (стрелки не читаются). Источник — съёмка с земли или панорамы.
- Карманы поворота и уширения перед перекрёстками не моделируются: нужен `split` пути у начала кармана. Механизм есть, правок пока нет.
- Узлы с крупными площадями (Театральная, пл. Победы, Касимовское × Грибоедова) сделаны одной площадкой SUMO, островки и «треугольники» не повторяются.
- residential и unclassified без `lanes` (большая часть города) не проверялись: автоматический замер ширины ненадёжен.
- `verify_markings.py` падает на подсчёте (`KeyError: 'nodes'` у пустого GLB-тайла). Это не связано с overrides: на текущем `game/public/world` то же самое. Виды сверху он успевает записать.

## Запуск

```bash
cd pipeline
uv run python verify_junctions.py --at 2400,-1700 --size 200 [--nodes]   # кроп для новой правки
uv run python build_world.py --out ../data/processed/world_test          # сборка с правками
uv run python verify_junctions.py --checks --before <net без правок> --after ../data/processed/world_test_work/net.xml
```

`net` без правок можно получить временным переименованием `roads.json`: без файла `overrides.py` ничего не делает.
